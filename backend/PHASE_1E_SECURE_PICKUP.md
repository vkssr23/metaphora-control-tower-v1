# Phase 1E — Secure Pickup Authorization and Chain of Custody Core

Phase 1E is the fail-closed human release gate between execution eligibility and pickup custody. A tenant-owned `pickup_release_cases` record freezes bounded references to the current load, Load Passport, accepted rate confirmation, cleared party-verification case, eligible execution-eligibility case, assignment, pickup instructions, facility and contact. Recommended indexes are `(tenant_id,id)`, `(tenant_id,load_id)`, `(tenant_id,status,updated_at)`, `(tenant_id,passport_id)`, `(tenant_id,pickup_authorization_id)`, and a partial unique active-case index on `(tenant_id,load_id)`; this phase does not apply indexes to a real database.

The lifecycle is `draft → review_pending → release_ready|review_required|blocked`, `release_ready → released|blocked`, `released → pickup_confirmed|exception|revoked`, with controlled returns from blocked, revoked and expired. Verdicts are `pending`, `release_ready`, `review_required`, or `blocked`. Status and verdict are server controlled. Ordinary updates cannot mutate a released case.

Mandatory prerequisites are always required: a current passport, accepted RC, cleared party case, eligible execution case, current driver/truck/trailer bindings, current pickup details, and no material drift. Missing data fails closed. The deterministic evaluator composes a controlled checklist and findings, normalizes text/email/phone conservatively, and uses exact normalized comparisons—never fuzzy or AI matching. Failures block; warnings require review; only owner/admin may waive eligible review items. Critical mandatory findings remain visible.

Final release is owner/admin-only. The server starts the audit, rereads prerequisites, recomputes readiness, conditionally writes passport-owned pickup authorization evidence with a deterministic evidence hash and passport version increment, then conditionally marks the case released. A passport race returns 409 without releasing. A later case race triggers conservative authorization revocation and returns 409; the passport is never rolled back to an older version. Duplicate active authorization is blocked.

Custody is an append-only embedded event ledger with server IDs, actors and timestamps. States include `not_authorized`, `authorized`, `driver_acknowledged`, `pickup_confirmed`, `exception`, and `revoked`. Manual pickup confirmation requires a released case and its matching active passport authorization. Exceptions preserve authorization ID, original issuance metadata and evidence hash while adding revocation metadata. No delete route exists.

Material changes to pickup location/contact/instructions, assignments, accepted RC, party clearance, execution eligibility, or passport state invalidate release readiness before the upstream mutation. Released cases move conservatively to exception and active authorization is revoked; no automatic reactivation occurs. The integration helper is intended for Phase 1B acceptance/supersession, Phase 1C block/expire/revoke/material change, Phase 1D block/expire/revoke/material assignment change, and canonical load mutations. Audit-start failure prevents primary mutation, tenant predicates are repeated on every read and conditional write, cross-tenant resources are reported as 404, and request schemas forbid unknown fields.

Only bounded metadata is retained. Raw documents, document content, signed URLs, credentials, authorization headers, tokens, database URLs, exception text, and arbitrary request dictionaries are excluded from release, authorization, custody, and audit records.

Phase 1E does **not** perform live identity verification, biometric verification, shipper verification, broker callback verification, facility verification, telematics verification, GPS verification, driver-app verification, physical custody verification, or fraud-provider verification, except when a future authoritative integration explicitly supplies that evidence. Future integration points may add authoritative provider evidence, driver apps, QR/NFC tokens, signatures, photos, GPS/geofencing, transactional outbox/workers, and production indexes without changing the human-controlled release policy.

## Phase 1E.1 release-safety corrections

The readiness evaluator is pure. Its caller supplies an explicit `evaluation_context.as_of`; the evaluator does not read a clock, generate randomness, or create timestamps. Routes take one server-controlled timestamp and apply it to persisted evaluation, checklist, and finding metadata. Identical logical inputs and the same `as_of` therefore produce byte-equivalent logical output.

The prerequisite snapshot freezes passport ID/version; accepted RC ID/version/revision/status/document; cleared Party Verification ID/version/status; and eligible Execution Eligibility ID/version/status. Evaluation and final release re-read tenant-owned records and compare every frozen relationship and version. Drift adds the stable `prerequisite_version_changed` blocker. Refresh is allowed only before release, rebuilds the snapshot, resets verdict/checklist/findings to pending, increments the case version, and requires a separate re-evaluation.

If passport activation succeeds but release-case finalization loses its race, cleanup conditionally revokes the exact authorization at the exact activated passport version and checks `matched_count`. A cleanup miss triggers a tenant-scoped reread. A confirmed revoked/expired/consumed state returns 409; an exact authorization still active returns sanitized 503 with failed reconciliation audit evidence. Passport versions only move forward and issuance evidence is preserved.

Pickup confirmation uses one pure binding validator covering tenant, authorization ID, load, passport, release case and release-case version, current driver/truck/trailer, active/non-revoked/non-expired state, and current passport relationship. Successful manual confirmation conditionally changes authorization `active → consumed` before updating custody. Consumed authorization cannot be reused or automatically reactivated.

Canonical parent routes own audit ordering: validate role, record, relationship and transition; begin the parent audit; then run Phase 1E safety invalidation; then existing Phase 1A/1C/1D invalidations and the parent mutation. The shared Phase 1E helper starts its bounded child audit only after the parent start and before safety writes. RC acceptance/supersession, Party Verification block/expire/revoke, Execution Eligibility block/expire/revoke, driver/truck master-data changes, and material load/assignment/pickup changes use this ordering. Released authorization is passport-first revoked before the release case and upstream record are changed. A lost safety race blocks the upstream write. If a later upstream mutation fails, the conservative invalidation and revocation remain; there is no automatic restoration.
